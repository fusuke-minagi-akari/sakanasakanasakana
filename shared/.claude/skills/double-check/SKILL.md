# /double-check — 直前の成果物を再検証

対象: `$ARGUMENTS`。空なら直前のターンで自分が出したもの全部。

## 1. 種類を判定

対象を下の4種に分ける(複数該当なら全部やる):

| 種類 | 例 |
|---|---|
| コード | 実装・diff・PR・ブランチ |
| 主張 | 調査結果・「Xは Y だ」系の断言・引用 |
| 数値/テスト | ベンチ結果・タクト・成功率・比較グラフ |
| 計画/選択肢 | 実装方針・どれをやるか・次の一手 |

## 2. 種類別チェック

### コード
- **正しさ**: 実際に動くか。エッジケース・エラー経路。可能なら実行/テストで確認(読むだけで済ませない)
- **簡潔さ**: 不要な行・抽象化・依存が無いか
- **モジュール性**: ロジックが正しい場所にあるか。既存ヘルパーを再実装していないか
- **リポジトリの流儀**: 周囲のコード・CLAUDE.md・CONTRIBUTING 等と命名/構成/慣習が揃っているか
- **影響範囲(blast radius)**: 変更した関数の呼び出し元を全部 grep。他ブランチ・open PR との衝突/依存(`gh pr list` で確認)

### 主張
- 各主張を**一次情報**(論文・公式ドキュメント・ソースコード・原ページ)で再確認。WebSearch の要約や subagent の報告は一次情報ではない
- 主張ごとに URL を付ける
- 判定: ✅ 確認済 / ⚠️ 未確認 / ❌ 誤り

### 数値/テスト
- 数値を再計算 or 再実行して一致を確認
- 比較の公平性: 同条件・同ハード・同入力・同ウォームアップ・同負荷か。CPU/GPU 競合など測定を歪める要因が無いか
- サンプル数とばらつき。1回の結果で結論を出していないか

### 計画/選択肢
- 各案の利点/欠点
- 今やるべきか(依存・優先度・誰がやるべきか)
- 要件自体がまだ曖昧なら、検証ではなく `/grill-me` を勧めて止める

## 3. 別視点で見る

自分の成果物を自分で採点しない。fresh な subagent(Agent tool)に対象と上のチェックリストを渡して独立に検証させ、自分の結果と突き合わせる。食い違いは一次情報で決着させる。

## 4. 修正

- 小さく明らかに正しい修正(typo・明白なバグ・誤った数値)はその場で直す
- それ以外は提案だけしてユーザー判断を待つ

## 5. 報告(短く)

```
**確認したもの**: <対象と種類>
**問題**: <各項目 + 証拠(file:line / URL / 再実行結果)>。無ければ「なし」
**修正済**: <直したもの>
**提案**: <ユーザー判断待ちのもの>
**判定**: ✅ go / ⚠️ 条件付き go(<条件>) / ❌ not yet
```
